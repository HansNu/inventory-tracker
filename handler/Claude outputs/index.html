Glossary — terms so far

Working definitions from Weeks 1–2 onward, in the corrected/settled form. Personal concepts.md is still the day-to-day habit — this is the static reference.

interface
A contract — a list of method signatures, nothing else. No logic, no fields. Anything with matching methods automatically satisfies it; Go never requires an explicit "implements" declaration.
DBTX
An interface (Close, Exec, Query, QueryRow) that anything usable as a database connection must satisfy. Lets a real *pgxpool.Pool and a fake test pool be swapped into the exact same spot in the code, unmodified. Lives in the repository package.
table-driven testing
A pattern, not a synonym for "unit test": define test cases as a slice of structs (input + expected output), then run them all through one shared loop instead of writing a near-duplicate function per case.
pgxmock
A fake implementation of pgx's interfaces, used in tests to simulate database responses (success, error, specific rows) without a real database.
mocking
Replacing a real dependency with a controllable fake so the thing being tested can run in isolation. Distinct from test input data (like a request payload) — a payload isn't a mock, it's just a fixture.
handler → service → repository
The clean-architecture split: handler only deals with HTTP (parse request, write response); service holds business logic; repository is the only layer allowed to touch the database.
layer-appropriate mocking
Each layer's test fakes the layer directly below it, not two layers down. A handler test fakes the service, not the database — that job belongs to a repository-level test.
init()
A function that runs automatically and unconditionally the moment a package loads — before main(), before TestMain(), before anything else. Every imported package's init() runs first, in dependency order, whether or not that package is actually used on a given code path.
concrete type vs. interface type
An interface variable is just a shape at compile time — the real type living inside it at runtime (*pgxpool.Pool vs. a mock) can be revealed with fmt.Printf("%T", value). Same line of code, different concrete type depending on what was wired in.
repository constructor (New___ pattern)
A function like NewAssetRepository(db DBTX) AssetRepository is not a test-only helper — it's the exact same function real production wiring uses (main.go calls it with the real pool). Only the DBTX value passed in changes between production and a test; the constructor and the struct it builds stay identical either way.
*string fields via JSON
A pointer field like Brand *string needs no special syntax in a JSON payload — encoding/json automatically allocates the pointer and fills it from a plain string value (and leaves it nil if the field is omitted). Pointers only require manual handling when hand-writing Go struct literals, like in test code.
